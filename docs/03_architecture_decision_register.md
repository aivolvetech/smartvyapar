# Architecture Decision Register (ADR)

This document tracks the core architectural decisions made for **Smart Vyapar** to satisfy the technical requirements of **BRD Version 2.0**.

---

## ADR-01: SQLCipher Database Encryption via Driver Adapter

### Context
BRD v2.0 mandates database encryption at rest. Prisma ORM does not support SQLCipher natively out of the box because its Rust query engine compiles standard SQLite.

### Approved Decision
Use **Option B (Raw SQLCipher Connection Driver)**. Prisma Client adapter is rejected because:
1.  **Peer Dependency Conflict:** It expects standard `better-sqlite3` and cannot resolve `better-sqlite3-multiple-ciphers` without unsafe package manager aliases.
2.  **CLI Rust Engine Incompatibility:** Prisma CLI tools cannot run migrations or db pushes on encrypted database files.
*   **Action:** Connect directly via `better-sqlite3-multiple-ciphers` and derive type-safe model interfaces directly from database schemas.

### Alternatives Considered
*   *Option A:* Upgrade Prisma to 6.7.0 to use the official `@prisma/adapter-better-sqlite3` adapter with SQLCipher.
*   *Option B:* Retain Prisma for schemas/types, but use a separate SQLCipher-capable library (e.g. raw better-sqlite3-multiple-ciphers or knex) for database access.
*   *Option C:* Replace Prisma entirely with a SQLCipher-compatible database layer.
*   *Option D:* Keep standard SQLite and use field-level encryption for selected sensitive fields, subject to formal BRD approval.

### Status
**Option A Rejected — Option B: Approved & Verified**

## ADR-02: Programmatic Startup Migration Runner

### Context
Standard Prisma migrations (`prisma migrate dev` or `prisma db push`) cannot connect to a SQLCipher encrypted database without unlocking it first, making traditional CLI migrations unusable in production.

### Decisions
1.  **For standard SQLite foundation (VERIFIED & APPROVED):**
    *   Perform schema migrations programmatically on startup by opening a direct connection via standard `better-sqlite3`, running WAL checks, and executing SQL migration files transactionally. This is fully working and verified.
2.  **For SQLCipher database foundation (PROPOSED & UNVERIFIED):**
    *   Modify the programmatic migration runner to open the database using the SQLCipher driver, unlock it with the encryption key (`PRAGMA key`), and execute compiled SQL migration files transactionally. This requires verification in the feasibility phase.

### Status
*   *Standard SQLite runner:* **Approved & Verified**
*   *SQLCipher encrypted runner:* **Approved & Verified**

## ADR-03: System Logging Migration to `electron-log`

### Context
A custom logging utility [logger.ts](file:///c:/Users/DELL7480/Desktop/Practice%20Project%2026/Mobile%20Smart%20Vyapar/electron/utils/logger.ts) was implemented in the initial foundation. BRD v2.0 requires `electron-log` for industry-standard file rotation, cross-process logging, and formatting support.

### Decision
Replace the internal implementation of `logger.ts` with `electron-log`. Keep the existing function interfaces (`logInfo`, `logError`) intact to avoid editing logging references throughout the codebase.

### Status
**Approved**

## ADR-04: Offline Hardware Fingerprinting for Licensing

### Context
Smart Vyapar must run completely offline. Traditional cloud licensing or OAuth verification is not feasible.

### Decision
Utilize motherboard UUID, BIOS serial numbers, and CPU details collected via multiple Windows CIM/system identifiers (using PowerShell CIM cmdlets or Node system APIs) to construct a unique machine signature. The offline activation key is generated by the vendor using a cryptographic signature of this signature. Fingerprint verification must allow tolerant multi-factor matching.

### Status
**Approved (Pending PoC-02 Verification)**
