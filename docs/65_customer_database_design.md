# Phase 6: Customer Database Design

This document details the schema design for the Customer Master in Smart Vyapar.

---

## 1. Customer Table Schema

The `Customer` table holds the master data for customers. It includes billing/shipping address detail, contact parameters, price book override associations, and active flags.

```sql
CREATE TABLE "Customer" (
    "id"                     TEXT NOT NULL PRIMARY KEY,
    "shopId"                 TEXT NOT NULL,
    "customerCode"           TEXT NOT NULL,
    "normalizedCustomerCode" TEXT NOT NULL,
    "name"                   TEXT NOT NULL,
    "normalizedName"         TEXT NOT NULL,
    "customerType"           TEXT NOT NULL DEFAULT 'RETAIL',
    "contactPerson"          TEXT,
    "phone"                  TEXT,
    "normalizedPhone"         TEXT,
    "alternatePhone"         TEXT,
    "email"                  TEXT,
    "gstNumber"              TEXT,
    "panNumber"              TEXT,
    "billingAddressLine1"    TEXT,
    "billingAddressLine2"    TEXT,
    "shippingAddressLine1"   TEXT,
    "shippingAddressLine2"   TEXT,
    "city"                   TEXT,
    "state"                  TEXT,
    "postalCode"             TEXT,
    "country"                TEXT NOT NULL DEFAULT 'India',
    "paymentTermsDays"       INTEGER NOT NULL DEFAULT 0,
    "creditLimit"            REAL NOT NULL DEFAULT 0,
    "priceBookId"            TEXT,
    "notes"                  TEXT,
    "isWalkIn"               INTEGER NOT NULL DEFAULT 0,
    "isActive"               INTEGER NOT NULL DEFAULT 1,
    "createdAt"              TEXT NOT NULL,
    "updatedAt"              TEXT NOT NULL,
    "version"                INTEGER NOT NULL DEFAULT 1,
    
    CHECK ("customerType" IN ('WALK_IN', 'RETAIL', 'WHOLESALE', 'DISTRIBUTOR', 'CORPORATE')),
    CHECK ("paymentTermsDays" >= 0),
    CHECK ("creditLimit" >= 0),
    CHECK ("isWalkIn" IN (0, 1)),
    CHECK ("isActive" IN (0, 1)),
    FOREIGN KEY ("shopId") REFERENCES "Shop"("id"),
    FOREIGN KEY ("priceBookId") REFERENCES "PriceBook"("id")
);
```

### Uniqueness and Indexes
To optimize searches and enforce data integrity:
- **Normalized Code Uniqueness**: Enforces that codes (case-insensitive, trimmed) do not conflict.
- **Normalized Name Index**: Optimizes auto-completion and dropdown search lists.
- **Normalized Phone Index**: Optimizes searches and matches during customer lookups.
- **GST / PAN Index**: Speeds up verification.
- **Walk-In Protection**: Only one Walk-In Customer allowed per shop.

```sql
CREATE UNIQUE INDEX "Customer_shopId_normalizedCustomerCode_key" ON "Customer"("shopId", "normalizedCustomerCode");
CREATE UNIQUE INDEX "Customer_shopId_isWalkIn_key" ON "Customer"("shopId", "isWalkIn") WHERE "isWalkIn" = 1;
CREATE INDEX "Customer_normalizedName_idx" ON "Customer"("normalizedName");
CREATE INDEX "Customer_normalizedPhone_idx" ON "Customer"("normalizedPhone");
CREATE INDEX "Customer_gstNumber_idx" ON "Customer"("gstNumber");
CREATE INDEX "Customer_isActive_idx" ON "Customer"("isActive");
CREATE INDEX "Customer_customerType_idx" ON "Customer"("customerType");
CREATE INDEX "Customer_priceBookId_idx" ON "Customer"("priceBookId");
CREATE INDEX "Customer_shopId_idx" ON "Customer"("shopId");
```

## 2. Integrity and Validation Rules

### A. Customer Code Uniqueness
- If not provided during creation, a customer code is generated sequentially (e.g. `CUST-000001`).
- The `normalizedCustomerCode` is generated by trimming and lower-casing `customerCode`. It must be unique per Shop (case-insensitive uniqueness).

### B. Phone Normalization
- `normalizedPhone` strips away all spaces, dashes, parentheses, and non-numeric characters (leaving only numeric base digits).
- The service will raise a soft warning (but not block creation) if another customer in the same shop has the same `normalizedPhone` to help prevent accidental duplication.

### C. Tax Identifiers
- **GSTIN**: Must match standard 15-character GST formatting rules (e.g., state code + PAN + alphanumeric + checksum).
- **PAN**: Must match standard 10-character alphanumeric PAN format.
- GST State code prefix must be validated against the customer billing/shipping state to prevent tax calculation conflicts.

### D. Walk-In Customer Seeding Policy
- The Walk-In Customer is marked with `isWalkIn = 1`.
- Cannot be deleted or deactivated (`isActive` must remain 1).
- Cannot have a custom credit limit (`creditLimit` must remain 0).
- Cannot have custom Price Books (always defaults to standard retail prices).
- Cannot receive an opening balance.
- **Idempotent Seeding**: Seeding is executed both at migration time (in SQL) and verified programmatically via `CustomerService` boundary immediately after a new Shop profile is saved. This double-layer ensures Walk-In existence without relying solely on migrations.
